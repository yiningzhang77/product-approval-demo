# 商家商品申请审批模块-升级实现规划

## 一、文档目的

本文用于规划如何把当前 `product-approval-demo` 从基础版升级到“商家端 + 管理端 + 分类基础资料 + 当前筛选结果导出”的增强版。

本规划只描述实现路径，不直接修改代码。

目标是保证：

- 功能闭环。
- 代码清晰。
- 便于 Java 初学者向导师解释。
- 不引入复杂权限系统。
- 不使用 Spring Security、JWT、Redis、微服务或前端框架。

## 二、最终实现边界

### 1. 技术边界

- Java 17
- Spring Boot
- Maven
- MySQL
- Spring MVC
- Thymeleaf
- Spring Data JPA
- 简单 CSS
- 统一 Thymeleaf 布局模板

不做：

- 真实登录
- 账号密码
- 权限系统
- Spring Security
- JWT
- Redis
- 微服务
- Vue / React 等前端框架

### 2. 业务边界

增强后系统分为：

```text
商家端
├─ 商家工作台
├─ 提交商品申请
└─ 我的申请

管理端
├─ 审批工作台
├─ 商品申请管理
├─ 价格告警
└─ 基础资料
   └─ 商品分类
```

商家端通过 URL 参数模拟当前商家：

```text
?merchantId=1
```

如果商家端页面缺少 `merchantId` 或商家不存在，建议显示错误提示，不默认使用第一个商家。

## 三、推荐实现总路线

建议分 6 个阶段实现，每个阶段完成后都可以单独启动验证。

```text
阶段 1：数据库与实体改造
阶段 2：统一查询条件与 CSV 导出
阶段 3：统一布局和侧边栏
阶段 4：商家端页面
阶段 5：管理端页面
阶段 6：分类基础资料维护与最终验证
```

原因：

- 数据结构先稳定，后续页面和查询才不返工。
- 列表查询和 CSV 导出先统一，避免两套逻辑不一致。
- 统一布局先搭好，后面页面复用侧边栏，不重复写菜单。
- 商家端和管理端分阶段完成，便于测试数据范围是否正确。

## 四、阶段 1：数据库与实体改造

### 1. 新增 merchant 表

用途：

- 保存商家基础信息。
- 商家端用 `merchantId` 限定数据范围。
- 管理端用商家列表做筛选下拉框。

建议字段：

```sql
CREATE TABLE IF NOT EXISTS merchant (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  enabled TINYINT(1) NOT NULL DEFAULT 1,
  created_at DATETIME,
  updated_at DATETIME
);
```

建议初始化：

```sql
INSERT INTO merchant (name, enabled, created_at, updated_at)
VALUES
('百姓超市', 1, NOW(), NOW()),
('万隆商城', 1, NOW(), NOW()),
('测试商家', 1, NOW(), NOW());
```

本阶段不做商家管理页面。

### 2. 新增 product_category 表

用途：

- 商家提交商品申请时从分类表下拉选择。
- 管理端按分类筛选。
- 管理端基础资料维护商品分类。

建议字段：

```sql
CREATE TABLE IF NOT EXISTS product_category (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  sort_order INT NOT NULL DEFAULT 100,
  enabled TINYINT(1) NOT NULL DEFAULT 1,
  created_at DATETIME,
  updated_at DATETIME
);
```

建议初始化：

```sql
INSERT INTO product_category (name, sort_order, enabled, created_at, updated_at)
VALUES
('食品饮料', 10, 1, NOW(), NOW()),
('服装鞋帽', 20, 1, NOW(), NOW()),
('数码家电', 30, 1, NOW(), NOW()),
('日用百货', 40, 1, NOW(), NOW()),
('美妆个护', 50, 1, NOW(), NOW()),
('运动户外', 60, 1, NOW(), NOW()),
('图书文具', 70, 1, NOW(), NOW()),
('其他', 100, 1, NOW(), NOW());
```

分类不做物理删除，只做启用 / 停用。

### 3. 改造 product_apply 表

当前表已有：

- `merchant_name`
- `category`

建议新增：

```sql
ALTER TABLE product_apply
  ADD COLUMN merchant_id BIGINT,
  ADD COLUMN category_id BIGINT,
  ADD COLUMN category_name VARCHAR(100);
```

建议保留：

- `merchant_name`
- `category_name`

理由：

- `merchant_id`、`category_id` 用于关联和筛选。
- `merchant_name`、`category_name` 作为申请提交时的名称快照，方便展示和导出。
- 即使后续商家名称或分类名称修改，历史申请仍保留提交时的信息。

是否删除旧字段 `category`：

- 第一版建议不急着删除。
- 可以先将新数据写入 `category_id` 和 `category_name`。
- 旧字段后续稳定后再考虑迁移或删除。

### 4. 新增或调整 Java 类

建议新增包和类：

```text
entity
├─ Merchant.java
├─ ProductCategory.java
├─ ProductApply.java
└─ ApprovalStatus.java

repository
├─ MerchantRepository.java
├─ ProductCategoryRepository.java
└─ ProductApplyRepository.java
```

`ProductApply` 需要新增字段：

- `merchantId`
- `merchantName`
- `categoryId`
- `categoryName`

第一版可以先不做 JPA `@ManyToOne` 关系，直接使用 ID 字段。

理由：

- 更容易讲清楚。
- 查询条件更直观。
- 避免初学阶段被懒加载、关联查询、序列化等问题干扰。

## 五、阶段 2：统一查询条件与 CSV 导出

### 1. 新增查询条件对象

建议新增 DTO：

```text
dto
└─ ProductApplyQuery.java
```

字段：

```text
merchantId
categoryId
keyword
status
isWarning
```

暂不实现：

```text
startDate
endDate
priceMin
priceMax
approvedStartDate
approvedEndDate
```

这些字段可以后续再加。

### 2. 统一列表查询方法

建议在 `ProductApplyService` 中提供：

```text
List<ProductApply> search(ProductApplyQuery query)
```

规则：

- 如果 `merchantId` 不为空，只查该商家。
- 如果 `categoryId` 不为空，按分类查。
- 如果 `keyword` 不为空，按商品名称模糊查询。
- 如果 `status` 不为空，按审批状态查。
- 如果 `isWarning` 不为空，按是否告警查。
- 默认按 `createdAt DESC` 排序。

实现方式建议：

- 第一版可以使用 Spring Data JPA `Specification`。
- 如果觉得 `Specification` 对初学者偏难，也可以用自定义 JPQL 查询。

推荐用 `Specification` 的原因：

- 多条件筛选更清晰。
- 列表和导出可以共用同一个查询。
- 后续加时间范围、价格范围比较方便。

### 3. CSV 导出共用 search 方法

所有导出接口都调用同一个查询方法：

```text
productApplyService.search(query)
```

不能再写一套单独导出查询逻辑。

CSV 必须：

- 加 UTF-8 BOM。
- 导出当前筛选结果。
- 商家端导出必须带 `merchantId`。
- 管理端无筛选条件时导出全部。
- 价格告警页导出默认带 `isWarning = true`。

## 七、阶段 4：商家端页面

### 1. 商家工作台

路径建议：

```text
/merchant/dashboard?merchantId=1
```

展示内容：

```text
数据卡片：
总申请数量
待审批数量
已通过数量
已驳回数量

待办提醒：

被驳回申请数量
价格告警申请数量

最近申请：
最近提交的 5 条申请
```

查询规则：

- 所有数据都必须按 `merchantId` 限制。
- 如果缺少 `merchantId`，展示错误提示。

### 2. 商家提交商品申请

路径建议：

```text
/merchant/apply?merchantId=1
```

变化：

- 不再手填商家名称。
- 根据 `merchantId` 读取商家名称。
- 商品分类从启用分类中下拉选择。
- 提交后写入：
  - `merchant_id`
  - `merchant_name`
  - `category_id`
  - `category_name`
  - `status = PENDING`
  - 价格告警字段

### 3. 商家我的申请

路径建议：

```text
/merchant/applications?merchantId=1
```

筛选条件：

- `keyword`
- `categoryId`
- `status`
- `isWarning`

默认排序：

- `createdAt DESC`

导出路径建议：

```text
/merchant/applications/export?merchantId=1&status=PENDING&categoryId=1&keyword=水杯
```

关键规则：

- 商家端导出必须限制当前商家。
- 页面导出链接要保留当前筛选参数。

### 2. 商品申请管理

路径：

```text

```

筛选条件：

- `merchantId`
- `categoryId`
- `keyword`
- `status`
- `isWarning`


### 2. 需要重点保持简单的地方

- `ProductApply` 不强制使用复杂对象关联，优先使用 ID 字段。

- CSV 导出统一放在 Service 或工具方法中，避免复制粘贴。
- 页面尽量复用片段，不重复写侧边栏。

## 十一、数据库迁移策略

由于当前项目已有基础表和可能已有测试数据，建议保守迁移：

1. 新增 `merchant` 表。
2. 新增 `product_category` 表。
3. 初始化商家和分类数据。
4. 给 `product_apply` 增加新字段。
5. 保留旧字段，不马上删除。
6. 新提交的数据写入新字段。
7. 如果需要兼容旧数据，可写一条简单迁移 SQL，将旧 `merchant_name`、`category` 尽量补齐到新字段。

第一版实现时，如果不要求保留旧测试数据，也可以清空 `product_apply` 后重新演示。

建议对考核演示：

- 直接重新初始化数据库。
- 保持数据干净。
- 准备 2 到 3 个商家和 8 个分类。

## 十四、主要风险与处理方式

### 1. 多条件查询容易分散

风险：

- 列表查询和导出查询写成两套，后续结果不一致。

处理：

- 必须统一走 `ProductApplyService.search(query)`。

### 2. 商家端数据隔离容易遗漏

风险：

- 商家端某些页面忘记带 `merchantId` 条件。

处理：

- 商家端 Controller 入口统一校验 `merchantId`。
- 商家端所有查询都必须显式传入 `merchantId`。

### 3. 分类停用影响历史申请

风险：

- 分类停用后，历史申请展示分类名称异常。

处理：

- 申请表保存 `category_name` 冗余快照。
- 停用分类只影响新申请下拉框，不影响历史申请展示。

### 4. 页面重复代码变多

风险：

- 每个页面都写一遍侧边栏和头部，后续维护困难。

处理：

- 使用 Thymeleaf `th:replace` 抽取公共侧边栏和顶部片段。

### 5. 当前商家入口不真实

风险：

- 没有真实登录，导师可能问当前商家怎么确定。

回答方式：

- 当前版本为了控制复杂度，不做账号登录。
- 使用 URL 参数 `merchantId` 模拟当前商家身份。
- 后续如果接入登录系统，只需要把 `merchantId` 从登录用户上下文中读取，列表和导出逻辑不用大改。

## 十五、第一版验收标准

第一版完成后，至少要满足：

- 数据库有 `merchant`、`product_category`、`product_apply`。
- 商家端必须带 `merchantId` 才能访问。
- 商家端只能看到自己的申请。
- 商家提交申请时分类来自分类表。
- 管理端可以看全部申请。
- 管理端可以按商家、分类、商品名称、状态、告警筛选。
- 价格告警页默认只看告警申请。
- 商品分类可以新增、修改、启用、停用。
- 所有列表默认最新申请在最上面。
- 所有 CSV 导出都跟随当前筛选结果。
- CSV 用 Excel 打开中文不乱码。
